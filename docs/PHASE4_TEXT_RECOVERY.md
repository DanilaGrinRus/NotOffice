# Phase 4 — rc.22: восстановление TXT/MD/RTF

## Поведение

- TXT/MD/RTF и новый Untitled.txt используют отдельный сеанс восстановления на
  окно. Сеансы имеют файловую блокировку; активное окно и сеанс, уже предложенный
  другому окну, не захватываются повторно.
- Снимок хранит тип и UTF-8 текст модели, длину и контрольную сумму. При restore
  текст не разбирается повторно как RTF/Markdown, объекты/скрипты не исполняются.
- Исходники не изменяются при checkpoint/restore. Восстановленная модель требует
  Save As копией; исходный путь и его файловый alias защищены. Для TXT без имени
  исходного пути нет. Сохранение внутрь LiteOffice-recovery отклоняется.
- Запись через отдельный pending-файл: sync, проверка, переименование в immutable
  snapshot. Хранятся новый и один валидный предыдущий снимок. Повреждённый новый
  даёт fallback. Когда все повреждены, выдаётся ошибка и данные остаются на диске.
- Интервал попыток 2 секунды плюс задержка UI/ОС. После сбоя доступен последний
  успешно записанный снимок; перед аварийным тестом дождаться статуса
  `Recovery checkpoint saved`. Ошибка записи явно оставляет последнюю модель
  в окне и сохраняет прежний успешный checkpoint.
- Save/Save As успешно завершён — сеанс очищается. Cancel/failed Save сохраняют
  его. Явное Don't save / подтверждённое удаление recovery очищают только выбранный
  сеанс. Later отпускает блокировки без удаления снимков.
- Обычное закрытие текста без несохранённых изменений очищает снимки, включая
  случай отмены всех правок до исходного состояния. Адресный тест сначала
  воспроизвёл устаревшее предложение восстановления, затем прошёл после исправления.
- Поддерживаются пустые правки (удалён весь ранее checkpoint-нутый текст), Unicode,
  кириллица и emoji. Снимок ограничен 32 MiB, входные/выходные текстовые файлы
  сохраняют прежние ограничения. Контрольная сумма обнаруживает повреждение,
  криптографическая аутентификация recovery не заявляется.

## Доказательства

Автоматически PASS: отдельный тестовый процесс держит четыре живых сеанса —
новый TXT, именованный TXT, MD и RTF. Во время работы discover не предлагает их.
После принудительного kill блокировки освобождаются, находятся четыре снимка и
восстанавливаются правильные типы и тексты; оригиналы защищены от перезаписи.

Также PASS: checksum/fallback, повреждение последнего после fallback, предыдущий
валидный снимок, отказ записи pending, пустой текст, буквальный RTF-подобный текст,
изоляция/эксклюзивное предложение, Save As/отказ/очистка, сохранность исходников,
восстановленный фокус через полный egui UI, close/cancel/Don't save.

Обычный полный автоматический набор включает существующие DOCX unit/integration
проверки. Ранее отложенная ручная регрессия печати/восстановления не запускалась.
Восстановление таблиц не добавлялось. Phase 4 остаётся PARTIAL.

Нативная ручная приёмка rc.22: NOT VERIFIED до результата пользователя. Принудительное
завершение тестового процесса и egui-тесты не объявляются проверкой настоящего окна.

## Короткая ручная проверка

1. Новый TXT: запустить rc.22, набрать уникальную фразу без сохранения. Дождаться
   `Recovery checkpoint saved`, завершить именно этот процесс через Диспетчер
   задач. Запустить rc.22 снова, Restore unsaved copy. Фраза должна вернуться;
   Ctrl+S должен предложить новый TXT, после Save As файл открывается с правками.
2. Повторить для TXT/MD/RTF из `manual_phase4_artifacts/text-rc11/`. Сделать правки,
   не сохранять, дождаться checkpoint, завершить процесс и восстановить. Save As
   пишет отдельный файл; исходники остаются прежними. В RTF сохраняется базовый текст.
3. Два окна с разными фразами: активное второе окно не должно попадать в список
   восстановления после сбоя первого. Его текст остаётся независимым.
4. В диалоге восстановления Later сохраняет копии до следующего запуска;
   после restore Cancel при закрытии сохраняет правки; успешный Save As и обычное
   закрытие не должны вновь предлагать уже сохранённую копию.

Все пользовательские TXT/MD/RTF для ручного теста сохранять под новыми именами.
Новые постоянные DOCX/PDF-артефакты в этом инкременте не создаются; автоматические
текстовые fixtures и snapshots находятся во временных тестовых каталогах.
